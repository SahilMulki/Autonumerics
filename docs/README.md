# docs

The **design record**: one architecture overview, seven implementation plans, and two measurement
ledgers — one recording what a pipeline run exposed, one recording a plan's before-and-after. None of it is loaded by an agent at runtime —
that is [`references/`](../references/) — though the manuals that *are* loaded cite these documents
for provenance, so a rule in the manual can be traced back to the measurement that produced it.
Nothing here is a tutorial. These are the documents that say *why* the pipeline is shaped the way
it is, and what was measured to find out.

Two house rules make the folder readable, and both are load-bearing:

- **Every plan carries a `Status:` line, and it is the authority on what shipped.** A plan is not a
  to-do list that rots; it is updated in place as the work lands, so `Status:` is the first thing
  to read and the only thing that should be trusted about completeness.
- **Superseded text is struck through, not deleted.** When a revision overturns an earlier claim,
  the old claim stays visible as `~~…~~` with the correction beside it. The point of these
  documents is that predictions can be checked against outcomes, which is impossible if the wrong
  predictions are quietly removed.

The two existing anti-hardcoding defences do not catch it, the CRN ladder already does (a pathwise-exact solver returns bit-identical states at every level, the reading `sde_bm_with_drift` has carried since it was written), and what is missing is the verdict rather than the detector. Implementing it mostly confirmed the plan, and the four places it did not are worth more than the code. The largest: **the benchmark's own SDE contract never accepted the Brownian increments at all** — the `dW` the plan said "the contract already accepts" belongs to the *kernel's* contract, while every benchmark problem statement rendered a four-argument signature and neither the inline path nor the sandbox had any way to supply one, so the route needed a contract extension and increment plumbing through the sandbox child beside it. The second: **the gate had to be measured before it could be set, and the first value was wrong** — 5% failed a *correct* Euler–Maruyama at 5.36%, which is precisely the false hard-fail this repo's calibration rule forbids and the kind that is invisible as a false positive, because what sets a strong-error gate is the scheme's discretization error and not the measurement's noise; at 10% a correct EM clears by 1.9x, a one-decision-wrong drift fails by 4.1x, and the two are separated by 7.6x. The third: **the exclusion needed two names rather than one**, since the ladder cannot distinguish a transcribed analytic solution from a constant and §2a.1 had just shown the constant case is real — so both are excluded but named apart, and the validator now refuses a vacuous entry at *authoring* time, which is what stops the stiff-quadratic problems being declared at SciML's horizon in step 6 and discovered in step 9. The fourth: **the leakage deny rules were already adequate and the hole was elsewhere** — `harvest.jl` is a `.jl` file under `benchmark/` and every interpreter in the deny list was a Python one. Rev 4 then authored the nine entries, with 66 tests of their own, and calibrated every gate both ways — which turned out to be one act rather than two, because **three entries were vacuous until calibration found them**. Every gate separates: a correct Euler–Maruyama clears by 2.0–7.3x, a one-decision-wrong variant fails by 2.2–238x, the narrowest separation is 4.4x against BENCHOP's 6.8x, and none was moved after the fact. The vacuity finding generalises the one step 2 made about the stiff triple: `additive` and `wave` are answerable by a **constant** at a default gate, because a strong error is normalised by the solution's magnitude while the information lives in the terminal law's spread, and the ratio of those two is a property of each problem rather than a universal tolerance — so those gates are 80x and 175x tighter, and both the validator and a per-entry test now refuse any entry a constant can answer. Two of the plan's own proposed controls had to be replaced: a dropped Milstein correction **is** Euler–Maruyama, a correct scheme of lower order rather than a wrong solver, and dropping β² from the stiff drift is unobservable where β² ≪ α — so the Itô/Stratonovich distinction is only measurable on that family where the noise itself is stiff. The replacement control for the cubic problem is the better one anyway: the drift sign flipped, which is what the library's own docstring says. The alternative to moving the stiff horizon that rev 2 had floated was measured and rejected rather than argued about — at SciML's `T = 3` a constant solver's relative timeseries error is 3.5e-13 at ten save points and still inside any usable gate at a thousand, because the transient is 0.3% of the interval. §10's prediction 4 is **falsified with its mechanism inverted**: the Monte-Carlo floor does set the weak problem's gate, not by forcing it wider but by putting a correct scheme's error *below its own standard error*, which also broke the validator's first convergence check and earned it the noise-floor abstention `crn.weak_order` already had. The weak entry's truth is derived rather than transcribed — its second moments satisfy a closed 3×3 system whose first row is exactly `[-1, 0, 0]`, which both gives `exp(-3)` to the bit and shows that **SciML's own graded observable cannot see the channel structure**, so the entry carries two more moments that can. And step 6 caught two defects in step 5: the exclusion was read before the pass decision, so a constant solver's degenerate ladder rescued it from a failure it had earned by up to 60x; and only the pipeline verdict knew about the exclusion at all, so a transcribing C0 baseline — the case the plan predicts is most likely — would have been recorded as a clean pass on all eight pathwise problems. Rev 5 closed the comparator track and the smoke test — steps 1, 3, 4 and 8 — and four of its findings change how the eventual result has to be read rather than confirming the plan. The harvest itself is 279 rows over 19 schemes with every cell clean, joined to the Python half by 72 sample-point checks of this repo's closed forms against the library's own `analytic` agreeing to 2e-16 — the run aborts rather than warns if they ever diverge, because a comparator table between two different problems still looks like a comparison. Measuring the stage counts instead of reading them off a tableau was a correction and not a refinement: `SRI` costs **ten** evaluation rounds per step and the three high-order weak schemes cost **nine**, driven by the diffusion rather than the drift, where a paper's tableau would have suggested two to four. And the work axis the whole adoption is built on turns out to disagree with measured seconds in a knowable direction: because these right-hand sides are three flops and the per-step cost is loop and noise overhead, a ten-stage scheme costs only 1.6× the seconds of a one-stage scheme, so `evals` **over-charges the multi-stage comparators by up to 6×** — and therefore flatters the one- or two-stage scheme the pipeline is expected to ship. The implicit schemes are the control, at 1.0×, because their extra drift evaluations are real nonlinear-solve iterations. That makes §10's prediction 1 ungradable as written: holding work fixed, the best Rößler scheme beats Euler–Maruyama by 36× to 1.7 million×; holding the error fixed at 1e-4 instead — which is the prediction's own phrasing — the work saved is 6.2×, 62.5×, 5.0×, 12.5×, 4.0×, 1.0×, 2.0× and, on the mixed-stiffness entry, **0.2×, meaning Euler–Maruyama wins there**. One prediction is confirmed cleanly: the EM anchor is not one number, and the measured spread is 8.1× against the >3× predicted — though the scalar half of it needed a second look, because 1.03× parity between numpy and compiled Julia is an artifact of a latency-bound chain of dependent multiply-adds, proved by interleaving four trajectories for a 2.6× speedup and by ruling out array layout at 1.04×, so the honest scalar ceiling is 2.71× and it ships as a third measured row rather than a footnote. The smoke test then found four defects, as its BENCHOP predecessor did: the per-plan ranking axis was **blank on eight of the nine entries** because the pathwise route is neither a field nor a moment nor a functional — the same defect one route later that BENCHOP's step 8 found for prices; **nothing in this repository had ever rendered a work-precision series**, which BENCHOP recorded as a nice-to-have for a later step and which here is the primary axis, so a nine-entry sweep would have collected forty-five points and displayed none of them; the report's methodology named two suites of the four that exist; and the per-plan record did not say which scheme each plan chose, which is step 10's own acceptance line verbatim. Re-ranking the nine pools offline retires two of the three candidate ranker fixes as measured-inert, **withdraws the resolution floor as harmful** (monotonic on sciml, opposite sign on the BENCHOP holdout, because a tie falls through to declaration order, which names the worst plan on 9 of 9 sciml pools and the best on 5 of 9 BENCHOP ones), and finds the one fix that crosses the line is in the **scorer**: `M01`'s index already ranks that pool correctly and `score` overrides it. §10g then makes that fix — the terminal-law KS gate was judged against `KS_C95 / sqrt(n)`, the Kolmogorov value, while the statistic standardizes by its own sample mean and standard deviation, which is the **Lilliefors** situation and has no closed-form null. A parametric bootstrap of the declared law replaces it, and it is **not** a loosening: 0.66–0.73× the old bar on a normal, a mild lognormal and a Feller-satisfying CIR, looser only on the two heavy-tailed laws it was mis-grading, and the normal case reproduces Lilliefors' published `0.886/√n` to within 2% — the one check on this bar that comes from outside the repo. Re-graded, M01's milstein goes 8 → 10 and **the arm reaches 0.931×, so the pipeline beats Opus answering cold**. Two costs are recorded rather than tuned away: Rademacher increments stop being caught at 625 steps, which is the CLT and not the bar (the old value “caught” them only in the sense that it failed a zero-error solver on five of nine seeds), and on a Feller-violating CIR the test has almost no power — a 1.18× margin where it used to read 48× of the wrong bar. §10h then prices the three ranker defects and ships one of three. The first two do not survive measurement, and for one shared reason: `comparable_keys`' all-four fallback is **dead code on all 18 recorded pools** — the two pools the step blamed on it were decided on correctly *restricted* sets — and the real defect, a shared set of one, cannot be fixed by abstaining, because every abstention route lands on **declaration order**, which is measured to be the pool's worst plan on 8 of 9 sciml pools (`1-euler-maruyama`, all nine) and its best on 5 of 9 holdout pools. That one fact retires `abstain`, re-withdraws the resolution floor under the new scorer, and explains all three §10f failures. Even the one non-fitted fall-through — prefer the higher *measured* order, a property of the method rather than a position in a list — stays unshipped: it takes sciml to 6/9 and 0.846×, but an **exact sampler has no order to measure**, so the closed forms that are the best plan in 7 of 9 holdout pools sort last, and holdout falls to 2/9 at the breadth where the gate first fires there. The third defect was the understated one. The per-plan record's field whitelist is not a reporting list but a **ranking input**, and it was dropping `order` and `structure` entirely, **fabricating** `accuracy` where the kernel had abstained — without `mc_se_rel`, `noise_limited()` returns False rather than “unknown”, so M05's three unresolved plans scored 0.141/0.008/0.046 and the pool ranked on that alone, putting the plan 651× worse first — and silently substituting a wrong `dynkin_bar` against a hardcoded 2.43 fallback, which no run would have caught and the new census test did. Twelve fields added, and a re-rank from the record now reproduces the conductor's own **bit-identically on all 18 pools**: 3/9 and 5.291× against the baseline becomes 5/9 and 0.931×. §10i then settles the pass-rate accounting, which is the number a reader would actually have quoted. `report._PASS_VERDICTS` required the pipeline to have **claimed** the pass as well as the harness to have confirmed it; the baseline constant it was compared against cannot carry that second conjunct, because a baseline has no self-score. ## Conventions inside a plan

- **Provenance labels** mark where each item came from: **[A]** already in this repo or the reference
  manuals, **[B]** adapted from the AutoNumerics paper-release pipeline, **[N]** new in this plan,
  **[C]** corrected against the shipped code, **[X]** built by this plan. A plan's final table
  usually carries the label beside each shipped item, which is the quickest map from rule to origin.
- **Numbers name their source.** The standing rule is that every figure is measured rather than
  quoted, with the command or test that produced it named so it can be re-run. Where a number was
  recalled rather than measured, that is stated.
- **`[rev]`, `[rev2]`, `[REV nn]`** mark text changed by a later pass, so the revision history is
  readable without `git log`.
